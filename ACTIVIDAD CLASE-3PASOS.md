| **#** | **Nombre del catálogo, o «ninguno»** | **¿Por qué este? (con algo del relato)** | **Uno que se parece pero no es (y por qué)** |
| --- | --- | --- | --- |
| **1** | **«ninguno»** | El soporte simultáneo de panel web y app móvil, así como la tolerancia a fallos ante caídas de mapas o IA, son requerimientos de **arquitectura de software e infraestructura** (BFF, Circuit Breaker, API Gateway, réplicas), no patrones de diseño orientados a objetos de GoF. | **Bridge** o **Facade**.<br><br>Se suele caer en la tentación de proponer *Bridge* pensando que «desacopla abstracción de implementación» (web/móvil compartiendo backend) o *Facade* para ocultar servicios caídos, pero Bridge desacopla jerarquías de herencia internas en código y Facade no resuelve caídas de red ni concurrencia. |
| **2a** | **Strategy** | El sistema requiere incorporar «nuevos algoritmos para calcular costos» basados en diferentes medios de transporte, peso, urgencia y distancia. Strategy encapsula cada algoritmo de tarificación en clases intercambiables en tiempo de ejecución. | **Template Method**.<br><br>Ambos manejan algoritmos, pero Template Method fija la estructura general en una clase base y delega pasos mediante herencia estática, mientras que Strategy usa composición para intercambiar el algoritmo completo sin atarse a una jerarquía. |
| **2b** | **Strategy** | El relato plantea «nuevos algoritmos para estimar tiempos de entrega» según variables dinámicas como tráfico, clima y distancia. Cada método de estimación es una estrategia de cálculo independiente de la entidad del pedido. | **State**.<br><br>State altera el comportamiento cuando el estado interno de la entidad cambia (ej. de *Pendiente* a *En camino*); aquí el estado del pedido no varía, sino la fórmula matemática/algoritmo inyectado para la estimación. |
| **3** | **Factory Method** | La empresa gestiona múltiples medios de transporte (Camionetas, Motocicletas, Bicicletas, Drones) con restricciones distintas y anticipa la incorporación de «nuevos medios de transporte». Permite delegar la instanciación del vehículo correcto sin acoplar el código a clases concretas. | **Builder**.<br><br>Builder se enfoca en construir un único objeto complejo paso a paso con configuraciones variadas; Factory Method se enfoca en decidir qué subclase concreta instanciar bajo una interfaz común. |
| **4** | **Observer** | El relato especifica que «cuando el estado de un pedido cambie, diferentes componentes del sistema podrían necesitar recibir dicha información: cliente, administrador, repartidor, notificaciones, estadísticas e IA». Modela una relación 1-a-Muchos donde el sujeto notifica eventos automáticamente. | **Mediator**.<br><br>Mediator centraliza la comunicación bidireccional compleja de muchos-a-muchos entre componentes acoplados; Observer es una suscripción unidireccional y desacoplada donde el emisor no necesita conocer a los receptores. |
| **5** | **Decorator** | El relato contempla «servicios adicionales para los paquetes, como seguro, entrega urgente o manejo especial» y la necesidad de combinar funcionalidades dinámicamente. Decorator permite envolver el envío base añadiendo costos y responsabilidades sin crear una explosión de subclases. | **Composite**.<br><br>Composite modela estructuras de árbol parte-todo para tratar colecciones y hojas de forma idéntica; Decorator no crea árboles estructurales, sino que envuelve un objeto individual para extender su comportamiento. |
| **6** | **Adapter** | La empresa busca no depender de un único proveedor de IA (pudiendo usar OpenAI, Anthropic o modelos propios) y advierte que «los servicios externos pueden tener interfaces y formas de comunicación diferentes». Adapter homogeniza interfaces heterogéneas a una interfaz común. | **Facade**.<br><br>Facade crea una interfaz simplificada para un subsistema propio complejo; Adapter no simplifica, sino que traduce/adaptas una interfaz existente e incompatible de un tercero a la firma requerida por nuestra aplicación. |
| **7** | **Facade** | El sistema debe interactuar con múltiples subsistemas externos e internos (mapas, geolocalización, pagos, notificaciones) y busca resolver «qué partes del sistema están adquiriendo demasiadas responsabilidades». Facade ofrece una interfaz unificada de alto nivel para coordinar estos servicios sin saturar a los clientes. | **Adapter**.<br><br>Adapter adapta una interfaz puntual incompatible; Facade agrupa y ofrece una puerta de entrada simple para operar un conjunto completo de subsistemas y librerías. |
